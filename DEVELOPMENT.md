# pi-claude-bridge development

For maintainers of this fork. [README.md](README.md) covers user-facing behavior; this file records invariants that span several modules.

## Invariants

- `src/models.ts::buildModels` maintains an explicit supported-model list and projects Pi metadata; it does not synchronize from SDK picker snapshots. Anthropic's [model configuration](https://code.claude.com/docs/en/model-config#work-with-fable) documents that Fable picker entries depend on organization availability and explicit selection can succeed without an entry. Fable metadata and effort support follow the [migration guide](https://platform.claude.com/docs/en/models/fable-5-1/migration-guide). `tests/unit-models.mjs` checks projection and metadata; `tests/unit-account-rotation-stream.mjs` checks the selected provider model reaches SDK query options.
- Request-owned state lives in a lane, never in a module-level binding. Pi calls one provider instance concurrently for parents, subagents and sibling conversations, so `src/request-lane.ts::runInRequestLane` keys an `AsyncLocalStorage` lane by `SimpleStreamOptions.sessionId`, and the active query context, Pi stream, pushed-context stack, watchdog and Claude session record resolve through it. A callback registered on a host-owned emitter (an `AbortSignal` listener) runs in the caller's context and must re-enter its lane explicitly. Presence is judged against `undefined`: an empty string is a named lane. The lane carrier and the per-session registries sit on `globalThis` under versioned symbols, because a parent and a child can load separate copies of the module. `tests/unit-session-lanes.mjs`, `tests/unit-foreign-conversation.mjs`.
- `session_shutdown` removes only the entries recorded for that `SessionManager` at its `session_start`, since an in-memory session forks by mutating the same manager's id. A request with `cacheRetention: "none"` (Pi's compaction and branch-summary one-shots, fresh `sessionId` each, no shutdown ever) releases its lane when it settles. `src/index.ts` around `ephemeralLane`.
- A tool-use turn ends at the stream's `message_stop`, because `message_delta` is what carries the real output-token count and the SDK invokes MCP handlers before it arrives. The early signals only arm the grace timer in `src/assistant-stream.ts::scheduleToolUseTurnEnd`, which force-finalizes a turn whose terminal events never come. A `message_stop` whose turn has tool calls but none that closed (the stream was cut mid-block) does not end the turn: Claude Code drops the half-built call and issues it again under a new id in its next message, so the bridge drops the unclosed blocks and the re-issued call joins the same Pi turn (`dropUnclosedBlocksAtMessageStop`, `tests/unit-cut-tool-call.mjs`).
- A tool result whose id was never registered in the active turn is refused, never queued against another call; the remaining handlers get an internal-error result so the turn cannot report success. A queued result whose handler has not fired by the next child message boundary is parked, still consumable, because the SDK staggers handler invocation. A query torn down with results outstanding writes diagnostics, marks the session for rebuild, and re-imports delivered results from Pi history next turn. `src/query-state.ts`, `tests/unit-tool-drain.mjs`, `tests/unit-queue.mjs`.
- User input Pi hands over with tool results (a steer, intercom) is written to the running query with `Query.streamInput()` before those results are released: `src/tool-result-delivery.ts::deliverSteerBeforeResults` resolves the MCP handlers only when the SDK pulls the next input item, which it does after `transport.write` resolved. The `streamInput()` promise settles at the query's result boundary, so it is never awaited. The message carries `priority: "next"`: on Claude Code 2.1.283, `"now"` answers the pending MCP call with an "interrupted" error and discards the real result, while `"next"` keeps the result and still reaches Claude's next request. Delivery is exactly once through the query's `UserMessageLedger`: an accepted steer is owned once, counts as accepted in `deliveredSuffix` (Claude Code keeps it as a queued-command attachment, and the digest is a logical delivery ledger), and never also enters `deferredUserMessages`, so the next turn resumes warm. Only a text-only callback, a callback whose results are all for calls Claude Code gave up on, or a steer arriving while an earlier write is still in flight defers to a continuation. A failed write releases no result, ends the Pi request with an error, marks the record for a rotated rebuild, and never replays the steer: whether Claude Code has it is unknown, and the rebuild re-imports it from Pi history. Abort, query end or a history replacement during the write also release nothing and leave the outcome to their own paths. The lane is not kept in use for a pending write, so the query may end and the next prompt may claim the lane's record first: the write's completion marks a record only while no newer query has claimed the context (`QueryContext.queryGeneration`, bumped only at fresh-query setup) and the record still names the Claude session it wrote into, never a replacement's (a rebuild may keep the session id). `tests/unit-live-steering.mjs`, `tests/int-tool-message.mjs`.
- When Pi replaces history while a query awaits a tool result, `src/index.ts::onPiHistoryReplaced` marks that query stale. The tool-result callback stops it, rotates the Claude session id to avoid racing the killed child's transcript writer, and imports Pi's new history with completed tool results before continuing. The stopped query's teardown drains its waiting MCP handlers with the cause `history-restart`, and `tool_calls_interrupted@history-restart` is `expected`: the drained answer reaches only the discarded child. If the child ran a connector or foreign MCP tool absent from Pi history, the query finishes on its original history and its persisted record requires a rebuild on the next turn. Query teardown must end the waiting callback stream even if the child's close throws. `tests/unit-compact-restart.mjs` covers these paths.
- Warm reuse of Claude Code's session is content-checked, not only count-checked. Claude Code resumes its own transcript, so every cursor write stores `historyDigest` (`src/history-digest.ts`) of Pi's messages `[0, cursor)` as the bridge imports them, plus `trailingAssistantDigest` for the reply Pi appends at the cursor, and REUSE requires both to match. A digest only ever describes history Claude holds: what REBUILD imported, a query's verified starting context, and then, at each tool-result callback, a suffix that must equal exactly what the bridge put into Claude's history since the last claim (`deliveredSuffix`: every reply delivered, in order, none missing or extra; results only for their calls and only if Claude received them; users only if this callback accepted them, written live or queued). The orphaned-result path, which delivers nothing, may add only results for calls the ended query made. A view that fails the check is never stamped; the record gets `UNVERIFIED_HISTORY_DIGEST` and `needsRebuild`, and restore keeps that mark. Records without a digest are accepted once and stamped. The digest covers order, roles, user text and images, assistant text and tool-call ids, exact Pi tool names and arguments. It deliberately ignores tool-result bodies and error flags, which pi-prune and pi-jev-pruner replace in every provider call, and thinking, system messages and metadata. `tests/unit-history-digest.mjs`, `tests/int-context-edit.mjs` (a same-length Pi `context_edit`).
- A rebuild never imports the latest assistant message with a thinking block removed: the API refuses a request whose latest assistant message's thinking differs from what it returned. So a trailing Claude turn with an unsigned thinking block (a stream cut mid-thought), and each one before it until the latest assistant replays exactly, is imported with its tool results as one user-side note. The turn wrote everything before any result came back, so the note lists its text and each numbered tool call's Pi name and arguments in the turn's own order, then each result's text and error flag by call number in history order, with nothing cut (`src/convert.ts::unreplayedTurnNote`). The note is a content array: a result's images are carried as the same image blocks the normal import builds, in their place among the results, and only an image without data or a MIME type is left as a text marker. The record's `historyDigest` still covers those messages as Pi has them, because Claude holds their content, so the next prompt's REUSE is legitimate. Each rebuild that writes a note records the silent incident `unreplayable_turn_imported_as_note`. `tests/unit-sync-shared-session.mjs`, `tests/unit-import.mjs`.
- An unpaired `tool_use` in a rebuilt session is paired with an explicit `is_error` result saying the output was lost, never a bare placeholder a model reads as output. `src/tool-pairing-audit.ts`.
- The provider is registered natively and unconditionally, once, by the primary module instance: `src/native-provider.ts::buildNativeProvider` through `pi.registerProvider`, with `auth.apiKey.check` and `resolve` answering from the existence-only credential probes in `src/auth-presence.ts`, so Pi hides the models while no account is connected. Pi's registration is upsert-by-id and replaces the stored object, so `PRIMARY_INSTANCE_KEY` and `ACTIVE_STREAM_SIMPLE_KEY` in `src/index.ts` keep a reloaded child module from swapping in its own `streamSimple` closure. A host below the peer floor gets `NATIVE_PROVIDER_UNSUPPORTED_MESSAGE` once instead of a wrong registration. Both native entry points route through the Claude Code subprocess; there is no raw API path, which is what keeps billing on the subscription.
- The stream-idle watchdog counts silence at any point of a live request, before and after the first output (`src/stream-idle-watchdog.ts`). It pauses only while the bridge itself is the holdup: Pi holds no stream because it is executing a tool, or an MCP handler waits for a Pi tool result; the clock restarts when that wait ends. Every SDK message resets it, and Claude Code 2.1.283 keeps a healthy child talking: API `ping` events arrive as `stream_event`s during long generations, every main-agent tool execution (connector calls included) emits a `tool_progress` heartbeat each 30s, and an `api_retry` notice extends the deadline by the backoff it announces. A child that stays silent anyway is a wedged child.
- Abort and idle-timeout teardown never waits on the child. The query leaves its lane synchronously (`src/query-state.ts::detachContext`), so a prompt Pi sends right after Esc starts a fresh query on a rotated session instead of joining the dying one, and the old context stops claiming the shared session record. `src/query-teardown.ts::abortSdkQuery` arms a settle grace that `src/consume-query.ts::consumeQuery` races every iterator step against, so handler drains, the `activeQuery` clear and the error to Pi happen even when `interrupt()` and `close()` leave the iterator pending forever. `tests/unit-query-lifecycle.mjs`.
- Nothing is written to disk without `CLAUDE_BRIDGE_DEBUG=1`, and no log line carries a tool payload or user-authored message content. `src/debug.ts`, `tests/unit-debug-discipline.mjs`, `tests/unit-debug-payload.mjs`.

## Child-executed tools

Pi's tools reach the child over the in-process MCP server, so a `tool_use` coming back is the child asking Pi to run something. claude.ai connectors run the other way: they are the child's own MCP servers, reachable only inside that process. So a `tool_use` under the connector namespace is never mirrored into the Pi stream: no `toolCall` block, no turn boundary, no expected-result entry (`src/connectors.ts::isChildExecutedTool`, applied at the emission sites in `src/assistant-stream.ts`). Mirroring one made Pi write a synthetic `Tool <name> not found` error beside an answer built from the real payload, and a rebuild projected that false result into the child's conversation of record.

The same rule covers Claude Code's in-process meta-tools (`ToolSearch`, `ScheduleWakeup`), matched by exact name in `src/connectors.ts::isChildInternalTool`, never by prefix. The MCP-resource built-ins stay mirrored: a resource read is a real account-surface access and consuming hosts audit it through the Pi mirror. The classifier is a namespace plus an exact-name set on purpose; "any name Pi cannot resolve" would also swallow a genuine tool-name mismatch, which must stay a loud dispatcher error. A non-bridge `mcp__<server>__<tool>` name and a bare name with no bridge manifest entry are refused at dispatch without widening the classifier; seeing a foreign MCP call commits account routing, a rejected naming slip does not.

Consequences:

- A connector tool must reach the model under one name. `src/convert.ts::mapPiToolNameToSdk` passes connector names through unchanged and `src/index.ts::resolveMcpTools` never re-offers a connector-namespace tool under the bridge prefix; Pi history recorded before that rule can still carry aliased names.
- The child's result is observed, never re-delivered (`src/assistant-stream.ts::noteChildExecutedToolResults`, fed from the SDK's `user` message). The debug line records name, error flag and byte size only.
- A connector call draws no tool card. Pi's assistant content is text, thinking or a `toolCall` its loop dispatches, so a delegated call has no honest representation; that is an upstream ask.

### The audit trail

Each child-executed connector call (never a child-internal built-in) appends a session `CustomEntry` of type `claude-bridge-connector-call` (`src/connector-audit.ts`). A `CustomEntry` does not enter LLM context and `convertPiMessages` reads messages, not entries, so it can neither be dispatched nor projected into the child. Never use `CustomMessageEntry` for this: that sibling type enters context, which is the bug again. The record is `{ name, toolUseId, outcome, byteSize?, childSessionId?, reason? }`, and `outcome` includes `unobserved` for a call whose result never came back, written at teardown with its cause; recording is keyed on the `tool_use` id so either path reaching a call first writes the one record. The audit map is query-scoped and is not cleared by `resetToolTracking`, which runs at every child message boundary. Pi's `createBranchedSession` copies entries into a fork, which is harmless here, unlike the `claude-bridge-session` marker beside it, which carries a `piSessionId` guard for that reason.

## Connector enforcement

- Write denial is two-layered: the known write tools are passed as `disallowedTools` by exact id (the CLI's MCP permission matcher takes exact names or a whole-server glob, nothing in between), and a `PreToolUse` hook denies any connector tool classified as a write at call time. Classification is fail-closed over the connector namespace: a tool is a write unless its name opens with a read verb matched as a word across naming styles, a leading server-name word skipped first; a name that opens with a read verb but also names a mutation is a write, and so is a name that does not parse. `src/connectors.ts::isConnectorWriteTool`, `tests/unit-connector-writes.mjs`.
- Every connectors-mode child also carries `src/connectors.ts::connectorBuiltinAllowlistHook`: only `mcp__custom-tools__*`, `mcp__claude_ai_*` and `CONNECTOR_DISCOVERY_TOOLS` may execute, and a hook exception converts to a deny because the CLI treats a thrown hook as fail-open. Connector sessions ingest untrusted third-party content, and a denylist of today's built-ins fails open on tomorrow's. The account probe child gets `denyAllToolsHook`.
- `settingSourcesForQuery` passes `["user"]` for connector queries and `[]` otherwise. `project` or `local` would let a checkout's `.claude/settings.json` reintroduce through `env` and `apiKeyHelper` exactly the provider-override environment `src/account-router.ts::subscriberProfileEnv` scrubs from managed children. An explicit `provider.settingSources` in bridge config wins verbatim.
- `enableConnectors` and `connectorWriteMode` resolve from user scope and the environment only (`src/config.ts::USER_SCOPE_ONLY_PROVIDER_KEYS`); project trust covers ordinary options and nothing that exposes live account data. `connectorWriteMode: "allow"` is per process, so an approved-write executor sets it in the child environment of a one-shot process.

## Config channels

`src/config.ts::loadConfig` reads `<piUserDir>/claude-bridge.json`, then a trusted project's `.pi/claude-bridge.json`. Provider options live under `provider`, and prompt replacement options live under `systemPrompt`. The loader normalizes provider values after merging both files. Connector enablement and write access remain user-scoped even for trusted projects.

## Runtime

- Pi loads `src/index.ts` directly and supplies `@earendil-works/pi-ai` and `@earendil-works/pi-coding-agent` at runtime, so they are optional peers and only installed as dev dependencies for typechecking and tests. `zod` is pinned to 4.4.3, the version dot314's bundle shipped when this repository dropped its own.
- Pi's TypeScript loader does not keep a reassigned `export let` in sync for importers, and on `/new`, fork, or resume it reuses the loaded modules while passing the extension a new API object. Shared module state is therefore read through functions such as `getExtensionApi()`. `npm run check:exports` rejects `export let` and `export var` in `src/`, and `tests/int-session-new.mjs` checks that the provider survives `/new`. Unit tests run under tsx, which keeps real ESM bindings and cannot catch this.
- Startup preflight (`src/claude-executable.ts::preflightClaudeExecutable`) preserves `code`, `errno`, `syscall`, `path`, `cwd` and the detected executable file type on the error it hands the SDK.

## Incidents

`src/incidents.ts` turns every anomaly into an incident keyed by `label@site`: a short id (`bi-` plus base36, never three digits in a row, because Pi's retry matcher looks for status codes such as 503 anywhere in an error text), a count, first and last seen, versions (bridge commit, Claude Code, Pi), the model, the flight-recorder snapshot and the diag entry reduced to metadata by `projectDiagMetadata`: ids, tool names, labels, sites and numbers, with argument property-name lists (`argKeys`) kept only as counts, because a tool may take free text as property names. Every string kept is validated by its kind: a tool_use id must match `(srv)toolu_01` plus 22 base62 characters, a message id `msg_01` plus 22, a session id a UUID or its 8-hex prefix, a version semver, and a site or cause a member of `INCIDENT_SITES`. A label must be a member of its finite code-owned set in `src/incident-labels.ts`, not merely label-shaped. A diag `kind` is a failure kind or `unclassified`. A `subtype` is an SDK result or system subtype the bridge handles. A `type` is a Pi assistant block type, and `why` is a stream-abandon reason. An unknown label becomes `[unknown <field>]`, and a diag `source` is not kept. The same checks cover the recorder snapshot's ids, the model and the versions. A recorder kind must be in `RECORDER_KINDS` (`src/flight-recorder.ts`), which also types `record()`. An SDK message type, subtype or stream event the bridge does not handle is recorded as `system_[unknown]`, `result_[unknown]`, `stream_event_[unknown]` or `message_[unknown]`, never as its own text. Evidence for a new Claude Code subtype is lost until the bridge handles it. A tool name is kept only if Pi offered that tool in a request of this process (`noteRegisteredToolNames`, fed by `resolveMcpTools`). Anything else becomes a placeholder such as `[invalid toolCallId]` or `[unregistered tool name]`. No text rule can tell a long identifier from a key, so evidence is never scanned for secrets; its shape leaves no room for one. `reportIncident` takes only sites from `INCIDENT_SITES`. `reportDiag` writes the diag entry exactly as `diagDump` always has, so every diag label goes through the class table `INCIDENT_CLASSES`:

- `user-visible`: Claude or Pi got a bridge-authored error; that text ends with ` (incident <id>)`.
- `silent`: an integrity mismatch, a forced rebuild or a dropped deferred message.
- `expected`: normal cleanup, counted only and never named in a text. Each entry needs code evidence at its site, which is why `partial_tool_calls_pruned`, `deferred_user_messages_dropped` and `tool_calls_interrupted` are split by site. `tool_calls_interrupted` is expected after an abort and after a restart on Pi's replaced history (`history-restart`), which re-imports Pi's history, tool results included, into a rotated session.
- `external`: Claude Code API errors other than account limits, and a Claude Code version change.

A bridge-authored error reaches Pi through two exits: the error event the provider pushes on its Pi stream, and a throw out of the provider call, which Pi's agent loop turns into an error message. `nameBridgeErrorEvents` and `nameThrownBridgeError` guard both. An error that names no incident gets `bridge_error@error-event` or `bridge_error@provider-throw`, and the suffix is added in place, so structured fields such as `resetAtMs`, `code` and `path` stay. The error text never enters the incident: from a thrown error only its name, `code`, `syscall` and `errno` are kept. Text written by Claude Code or the API reaches Pi unchanged, because the bridge registers it with `markExternalError` where it receives it: SDK construction and iterator throws, result errors, the SDK's error copy and rejected rate-limit events. The exception is an SDK throw that the bridge wrote (`sdkErrorText`, `isBridgeClaudeError`): its executable preflight error, its spawn diagnostic, or the SDK's rewrap of that diagnostic ("Failed to spawn Claude Code process: …" or "Cannot write to process that exited with error: …"), recognized by the fixed wording `CLAUDE_SPAWN_FAILED_WORDING`, which the SDK's token redaction leaves alone. Those get an incident. A failure while naming still delivers the error as it was.

From a fresh request's entry until its SDK query starts, the lane's `QueryContext.preQueryModel` holds the requested model. An incident recorded then, whatever its site, takes that model, `phase: "before-query"` and `snapshot: null`. It never takes the recorder or turn output, which still belong to the previous query.

The flight recorder (`src/flight-recorder.ts`) keeps the last 256 events of each query: SDK message and stream event types, tools/call arrivals, claims and answers, results queued, parked and delivered, cursor moves, aborts and timeouts. It is always on because the evidence is needed the first time a race happens, not after someone turns debugging on; so it does no I/O and no formatting, and consecutive deltas of one block share a record.

Only a user-scoped `incidents.repo` enables the store, `<piUserDir>/claude-bridge-incidents.jsonl`: one line per new signature and per count update, batched on a timer, written asynchronously with mode 0600 and rotated like the debug log. It also remembers the last Claude Code version seen, and a rotation starts the fresh file with that version so the next process can still compare against it.

The bridge never files an incident on its own. The agent decides, with the `claude_bridge_incident` tool (`src/incident-tool.ts`), which is registered once at every load, with or without `incidents.repo`, so the tool list is the same for the whole process. It sets no `promptSnippet`. Its `action` is one of three:

- `list`: the incidents recorded in this process, newest first, without `expected` ones, at most 20 rows. Each row gives the id, what happened, the label and site, the class, the count, and first and last seen.
- `show` with `incident`: what happened, what the user saw, the evidence table, the diag metadata and the latest recorder snapshot. It is the same validated projection an issue carries, under 24 KB.
- `file` with `incident`: files the incident (`src/incident-filer.ts`). It needs `incidents.repo`; without it the tool refuses, says where the user sets it, and runs no `gh`. The tool takes no text from the agent: the issue carries only the bridge's recorded evidence, and the agent gives its analysis to the user in chat.

The incident registry is process-global (a `Symbol.for` key), because Pi loads a fresh copy of every module of the bridge for each session it starts with its own loader (an in-process subagent) and on `/reload`. The copy that serves the requests records their incidents, and every copy's tool and `/pi-claude incidents` read the same registry.

Filing goes through `gh --repo` with a 30-second timeout and `GH_PROMPT_DISABLED`. It first searches the repo's open issues for the marker `<!-- claude-bridge-incident: <signature> -->`. If one carries it, the bridge comments on it with the latest evidence, which is how separate processes file a signature once. Otherwise it creates an issue titled `[incident] <label> at <site> (<class>)`. The body opens with the marker, says what happened and what was seen, then gives the evidence table, the recorder snapshots, the diag metadata and a test file that drives the same path, all under 60 KB. The bridge builds every title, body and comment itself; no text the agent writes is published. An incident is filed at most once per process: filing it again returns its issue without running `gh`, and a call made while the first is still running waits for it. The tool call waits for `gh` and returns the issue number and URL, telling the agent to tell the user the number and its own analysis in chat. A failed `gh` is a tool error with a short reason (`gh-missing`, `gh-auth`, `timeout`, ...). It is not a filing, so the agent may try again. Only a signature made of `INCIDENT_CLASSES` and `INCIDENT_SITES` is filed. The unit tests put a failing `gh` stub first on `PATH` (`tests/lib/test-env.mjs`), so no test can reach GitHub.

The incidents repo may be public, so everything filed is treated as public. A published value is a member of a set the code or the runtime owns, a validated random id, a number or a boolean. A value that only has the right shape is not enough, because a project's own error class, error code or version suffix can name the user or the project. The publishing step (`publishedDiag`, `publishedVersion` and `publishedModel` in `src/incidents.ts`) applies these rules to a body or comment:

- Tool names: a Pi built-in (`read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`, or the name the bridge serves one under, `mcp__custom-tools__<name>`) and the bridge's own `claude_bridge_incident` stay. Any other becomes `tool-` plus 8 hex characters of its SHA-256, the same in every process: a name like `mcp__<company>__deploy` says what a user runs.
- `errorName`: the JavaScript built-in error names, `AbortError`, `TimeoutError`, `SystemError`, the bridge's own error names and the names the Agent SDK gives its errors. Anything else becomes `[unknown error name]`.
- `code`: an errno name of the running Node (`os.constants.errno`), a Node `ERR_` code, or a code the bridge's spawn errors set. Anything else becomes `[unknown code]`.
- `syscall`: Node's and libuv's syscall names, and the bridge's preflight `chdir` and `exec`. Anything else becomes `[unknown syscall]`.
- Claude Code and Pi versions, in the evidence table and in the diag: the numeric `major.minor.patch` only. A prerelease suffix becomes `-[suffix]`; a version with build metadata (`+…`) is rejected at recording and publishes as `[invalid version]`.
- Model: a model the bridge registers (`MODEL_IDS_IN_ORDER`, `src/models.ts`). Anything else becomes `[unregistered model]`.
- Everything else is published as recorded, and each value is code-owned, random or numeric:
  - the title, signature, marker, class and site (the class and site tables), the description and the fixed prose;
  - the incident id (random), the phase, UTC timestamps, counts and the diag's other numbers, booleans and argument-key counts;
  - the bridge commit (12 hex of the bridge checkout's HEAD);
  - recorder kinds (`RECORDER_KINDS`) and diag label fields and roles (finite sets);
  - tool_use, message and session ids (validated random ids).

Paths, cwds, error messages and every other string of no known kind are dropped at recording. `list`, `show` and `/pi-claude incidents` show the evidence as recorded, with the real tool names, error labels, versions and model, since they never leave the user's machine.

Invariant: a diag object's keys are literal keys written at the bridge's `reportDiag` and `reportIncident` call sites, never built from data such as an id, a name or a path. Projection keeps any key that matches `FIELD_NAME` and lists a dropped field by its key path in `droppedFields`, and both are published, so a call site that keyed an object by data would publish that data. Put such data in an array of objects under a literal key instead.

Every title, body and comment passes `sanitizeForIssue` (`src/incident-sanitizer.ts`), the repository's no-tagging rule reimplemented for runtime: it removes handles (emails and npm scopes stay), `owner/repo#N` references to other owners, links to other repositories' issues, PRs, commits and discussions, and co-author lines. Issue bodies and comments are built from validated evidence and fixed bridge prose only, so nothing is scanned for secrets.

Notices (`src/incident-notice.ts`) are always on, with or without `incidents.repo`. A `user-visible` or `silent` incident is told to the Pi session whose request hit it, once per signature per session. Workarounds for Claude Code misbehavior, such as `tool_call_abandoned_by_claude_code`, are `silent` and so are told. `external` incidents (a plain API error, a Claude Code version change) and `expected` cleanup never are; `list` still shows the external ones. Everything pending for a session goes out as one `claude-bridge-incident` message: it has a line per incident (id, what happened, label and site, and whether an error was shown or the bridge recovered) and a closing line that points at `claude_bridge_incident show`. With a repo that line also points at `file`; without one it says filing is off. The session's own copy returns the message from its `before_agent_start` handler. Pi 0.87.1 puts that message after the user's prompt and after any next-turn messages (`agent-session.js`, `prompt()`), and `convertToLlm` turns it into a user message. A result with only `message` leaves the system prompt options, and so the system prompt and the tool list, unchanged. To the bridge that is an ordinary trailing batch of user input, so the turn reuses Claude's session, and the history digest covers the notice from then on. The bridge never calls `sendMessage` or starts a turn for an incident, so a notice waits for the user's next prompt; a steer or follow-up queued while the agent runs does not run `before_agent_start`. Incidents are recorded by the copy serving the requests, while each session (an in-process subagent too, and every session after `/reload`) runs its own copy's handler. So the pending incidents and the signatures each session was told are kept process-global, by Pi session id, for the 64 sessions most recently noticed or prompted. A reload keeps the session id, and with it what the session was told and what it still has pending.

## Rate limits

`src/rate-limit.ts::normalizeRateLimitUtilization` reads a value in `(0, 1]` as a fraction and `(1, 100]` as a percent; exactly `1` is ambiguous and resolves to full, the fail-closed direction. `formatAllowedRateLimitWarning` emits a neutral toast from `ALLOWED_RATE_LIMIT_WARNING_UTILIZATION_THRESHOLD` up and never quotes a `% used` figure. Rate-limit errors are deduplicated before notification and emitted as `pi-claude:rate-limit`.

## Tests

```bash
npm run typecheck
npm run test:unit      # node --test over tests/unit-*.mjs, no credentials
npm run test:ci        # typecheck, then the unit suite
npm test               # unit, then the integration suites
npm run test:usage     # A/B subscription-usage comparison against Claude Code direct
```

`test:unit` preloads `tests/lib/test-env.mjs`, which points `PI_CODING_AGENT_DIR` at a scratch directory so unit tests never read the real `claude-bridge.json` or append to the real bridge logs. To run one file, keep the preload: `node --import tsx --import ./tests/lib/test-env.mjs --test tests/unit-foo.mjs`. `tests/unit-test-env.mjs` fails when it is missing. The integration harnesses give every suite its own debug and diag log under `.test-output/`.

The integration suites (`tests/int-*.sh`, `tests/int-*.mjs`) need the `pi` CLI and a logged-in Claude Code; `tests/int-session-resume.mjs` also needs `CLAUDE_BRIDGE_TESTING_ALT_MODEL` and `CLAUDE_BRIDGE_TESTING_ALT_PROVIDER` from `.env.test`, which `npm test` sources when present. They also need a `claude-bridge.json` with `systemPrompt.replacement` in the agent directory they run under (`PI_CODING_AGENT_DIR`, else `~/.pi/agent`); without one the bridge refuses Pi's main prompt and every Claude turn fails. The shell suites bound each run with `run_with_timeout` from `tests/lib/bash-setup.sh` because macOS has no `timeout`. `test:usage` spends real subscription usage. A test that spawns a child pins `HOME`, `PI_CODING_AGENT_DIR` and `CLAUDE_CONFIG_DIR` explicitly, because a spawned child inherits the process's start environment rather than a harness override.

## Syncing with dot314

This repository is `git subtree split --prefix=extensions/pi-claude-bridge` of [w-winter/dot314](https://github.com/w-winter/dot314) plus local commits. Splitting dot314 again produces the same commit ids, so its bridge changes merge normally. In a dot314 clone with `upstream` pointing at w-winter/dot314:

```bash
git fetch upstream
git subtree split --prefix=extensions/pi-claude-bridge upstream/main -b bridge-upstream
```

Then, in this repository:

```bash
git fetch <dot314 clone> bridge-upstream
git merge FETCH_HEAD
```

Upstream commits regenerate `bundle/index.js`, which this repository does not keep. Resolve those conflicts with `git rm -r bundle`.
