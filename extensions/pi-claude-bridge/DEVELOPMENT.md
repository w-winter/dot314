# pi-claude-bridge development

For maintainers of this fork. [README.md](README.md) covers user-facing behavior; this file records invariants that span several modules.

## Invariants

- `src/original-tool-inputs.ts` parses SDK `wire_tool_inputs` and transcript `wireToolInputs` as ID-keyed argument objects. `QueryContext.queryOriginalToolArgs` keeps mapped originals across re-yields; the existing normalized maps still pair MCP invocations. Complete streamed JSON supplies originals when API metadata is absent. Handler-first calls with no original source retain validated handler input. Distinct originals with equal normalized arguments require a tagged callback. Native matching applies recorded originals before both streamed and imported comparisons. `tests/unit-wire-tool-inputs.mjs` and `tests/unit-native-wire-prefix.mjs` exercise execution and replay.
- `src/continuation-prompts.ts` defines the exact history-restart, failed-reply, instruction-change and host-resume prompts shared by the provider and native matcher. A matching native prompt is copied only before a verified next group. Changed or mixed text ends the prefix. System-instruction changes still restart with Pi's current prompt.
- An SDK attempt completes at `message_delta`. A `message_stop` alone can be Claude Code closing an abandoned attempt before a retry. Live blocks keep their indexes for delayed Pi consumers; the terminal message excludes abandoned blocks. `tests/unit-nonstreaming-fallback.mjs` covers streamed and completed-message retries.
- `src/direct-auth.ts::hasDirectClaudeLogin` uses the child environment and `settingSourcesForQuery` for direct-account availability. An `apiKeyHelper` counts only when user settings load. Registration, pre-spawn checks and native auth share the predicate; an external account router can establish availability independently. All SDK query paths set `settings.autoDreamEnabled` to `false`. Provider queries also set `CLAUDE_CODE_ELEGANT_MEADOW=0` to suppress extra API-request transcript records. `tests/unit-direct-auth.mjs`, `tests/unit-background-settings.mjs` and `tests/unit-child-env.mjs` check these boundaries.
- Pi's assistant usage represents the latest underlying Claude request, not aggregate subscription consumption. `QueryContext.beginChildMessage` resets counters on a different message ID; streamed and completed copies of the same ID share counters. `resetTurnState` clears the identity for the next Pi message, while a deferred continuation keeps displayed content until its next Claude message replaces usage. `src/assistant-stream.ts::updateUsage` projects that message's counters; reasoning and `cacheWrite1h` are subsets of output and cache writes. `tests/unit-child-executed-tools.mjs` and `tests/unit-continuation-dedup.mjs` exercise Pi's actual context-size, compaction and overflow functions.
- `consumeQuery` retains an unmanaged rejection in `QueryContext.rejectedClaudeLimit` before checking for a live Pi stream. Each SDK query, including a deferred continuation, starts with no retained rejection; a success result clears it only when `is_error !== true`. `src/index.ts::surfaceFailure` formats terminal failures with that quota cause, except for cancellation and usage-credit policy stops. The idle watchdog still interrupts and marks the transcript for rotation but emits no `stream_idle` resume event after rejection. `tests/unit-rate-limit-authority.mjs` checks terminal failures against Pi's retry classifier.
- Memory of shown rate-limit warnings belongs to the UI recipient, in a process-global weak map in `src/bridge-state.ts`. Keys distinguish accounts, status and limit type; values hold the last shown reset time, including explicit absence. Delivery failure consumes no notice state. `startFreshQuery` captures `noticeAccountKey` from the selected profile or the child environment's resolved Claude directory and passes it through deferred consumption. Account directories stay in memory. Request events and router bookkeeping run independently of toast delivery. `tests/unit-rate-limit-notice-once.mjs` covers concurrent requests, recipient replacement and account changes.
- Each new Claude Code query sends Pi's current system prompt, rendered from all of the request's system messages. At a tool-result callback, the bridge compares the rendered outbound prompt with the query's initial prompt. A change restarts the query on Pi's history with a rotated Claude session ID to avoid the old child's transcript writes. Completed tools are imported rather than executed again. Calls executed inside Claude Code and absent from Pi's history prevent a safe restart; the bridge reports an error and cancels the query. Tool-only updates keep the running query. A changed prompt may invalidate Claude's prompt cache. `tests/unit-compact-restart.mjs` covers restart and tool-result replay.
- `src/models.ts::buildModels` maintains an explicit supported-model list and projects Pi metadata; it does not synchronize from SDK picker snapshots. Anthropic's [model configuration](https://code.claude.com/docs/en/model-config#work-with-fable) documents that Fable picker entries depend on organization availability and explicit selection can succeed without an entry. Fable metadata and effort support follow the [migration guide](https://platform.claude.com/docs/en/models/fable-5-1/migration-guide). `tests/unit-models.mjs` checks projection and metadata; `tests/unit-account-rotation-stream.mjs` checks the selected provider model reaches SDK query options.
- Request-owned state lives in a lane, never in a module-level binding. Pi calls one provider instance concurrently for parents, subagents and sibling conversations, so `src/request-lane.ts::runInRequestLane` keys an `AsyncLocalStorage` lane by `SimpleStreamOptions.sessionId`, and the active query context, Pi stream, pushed-context stack, watchdog and Claude session record resolve through it. A callback registered on a host-owned emitter (an `AbortSignal` listener) runs in the caller's context and must re-enter its lane explicitly. Presence is judged against `undefined`: an empty string is a named lane. The lane carrier and the per-session registries sit on `globalThis` under versioned symbols, because a parent and a child can load separate copies of the module. `tests/unit-session-lanes.mjs`, `tests/unit-foreign-conversation.mjs`.
- `session_shutdown` removes only the entries recorded for that `SessionManager` at its `session_start`, since an in-memory session forks by mutating the same manager's id. A `/reload` is that shutdown followed by a `session_start` with reason `reload` in a new module copy, and that start restores the record from Pi's marker as `startup` does, so the next prompt can resume warm. It skips the restore when a Claude Code child may still be writing that transcript: the shutdown found a query still in the lane, or the lane's record carries `forceRotate` (an aborted or killed query leaves the lane at once while its child exits, and the shutdown cancels the persist that would have saved the mark). The shutdown reads both before it clears the lane (`tests/unit-reload-restore.mjs`). A request with `cacheRetention: "none"` (Pi's compaction and branch-summary one-shots, fresh `sessionId` each, no shutdown ever) releases its lane when it settles. `src/index.ts` around `ephemeralLane`.
- `session_shutdown` closes every query of that session (its lane and fork lanes) that has no live Pi stream. Pi cancels a running turn before a session ends, but a query outlives its run when a tool batch whose every result says `terminate` ends the run (pi-subagents' `structured_output`) while Claude Code still waits for those results; once the lane is gone no callback reaches it, and its child would wait until Pi exits. A query still streaming to Pi (RPC reload does not wait for the reply) is marked `sessionEnded` and leaves the record at once: its reply finishes, and if it ends at a tool call, `endToolUseTurn` closes the query. `tests/unit-shutdown-closes-query.mjs`.
- A query starts Claude Code in the directory of the Pi session it serves, never assumed to be the process's. Pi passes providers no directory, and pi-subagents runs a foreground child inside the parent's process, in the child's worktree. Claude Code's first prompt names its start directory as the model's "Primary working directory", and the session record, Claude Code's transcript path and the project `claude-bridge.json` read all follow it. So the live-session registry in `src/pi-sessions.ts` maps each Pi session id to the `ctx.cwd` of its `session_start`, its shutdown removes the entry, and `piSessionCwd` resolves a request's `sessionId` to it; a session this process did not start (a one-shot with a fresh id) uses `process.cwd()`. A host's `options.cwd` wins. `tests/unit-session-cwd.mjs`.
- A tool-use turn ends at the stream's `message_stop`, because `message_delta` is what carries the real output-token count and the SDK invokes MCP handlers before it arrives. The early signals only arm the grace timer in `src/assistant-stream.ts::scheduleToolUseTurnEnd`, which force-finalizes a turn whose terminal events never come. A `message_stop` whose turn has tool calls but none that closed (the stream was cut mid-block) does not end the turn: Claude Code drops the half-built call and issues it again under a new id in its next message, so the bridge drops the unclosed blocks and the re-issued call joins the same Pi turn (`dropUnclosedBlocksAtMessageStop`, `tests/unit-cut-tool-call.mjs`).
- A tool result whose id was never registered in the active turn is refused, never queued against another call; the remaining handlers get an internal-error result so the turn cannot report success. A queued result whose handler has not fired by the next child message boundary is parked, still consumable, because the SDK staggers handler invocation. A query torn down with results outstanding writes diagnostics, marks the session for rebuild, and re-imports delivered results from Pi history next turn. `src/query-state.ts`, `tests/unit-tool-drain.mjs`, `tests/unit-queue.mjs`.
- User input Pi hands over with tool results (a steer, intercom) is written to the running query with `Query.streamInput()` before those results are released: `src/tool-result-delivery.ts::deliverSteerBeforeResults` resolves the MCP handlers only when the SDK pulls the next input item, which it does after `transport.write` resolved. The `streamInput()` promise settles at the query's result boundary, so it is never awaited. The message carries `priority: "next"`: on Claude Code 2.1.283, `"now"` answers the pending MCP call with an "interrupted" error and discards the real result, while `"next"` keeps the result and still reaches Claude's next request. Delivery is exactly once through the query's `UserMessageLedger`: an accepted steer is owned once, counts as accepted in `deliveredSuffix` (Claude Code keeps it as a queued-command attachment, and the digest is a logical delivery ledger), and never also enters `deferredUserMessages`, so the next turn resumes warm. Only a text-only callback, a callback whose results are all for calls Claude Code gave up on, or a steer arriving while an earlier write is still in flight defers to a continuation. A failed write releases no result, ends the Pi request with an error, marks the record for a rotated rebuild, and never replays the steer: whether Claude Code has it is unknown, and the rebuild re-imports it from Pi history. Abort, query end or a history replacement during the write also release nothing and leave the outcome to their own paths. The lane is not kept in use for a pending write, so the query may end and the next prompt may claim the lane's record first: the write's completion marks a record only while no newer query has claimed the context (`QueryContext.queryGeneration`, bumped only at fresh-query setup) and the record still names the Claude session it wrote into, never a replacement's (a rebuild may keep the session id). `tests/unit-live-steering.mjs`, `tests/int-tool-message.mjs`.
- Claude Code reads a message with a text block that starts with `/` as one of its own slash commands: a fresh prompt like `/review this` runs the command and never reaches Claude, and a message queued mid-turn whose last block starts with `/` (a pasted path too) is held until the turn ends. Pi has already run its own commands, so `src/user-prompt.ts::slashLed` marks such a prompt, continuation or steer `client_composed: true`, which Claude Code delivers as written. It also skips Claude Code's per-turn reminders on that turn, so plain messages never carry it. The stored prompt record keeps the same content, plus a `queueSkipAttachments` field. `tests/unit-live-steering.mjs`.
- When Pi replaces history while a query awaits a tool result, `src/index.ts::onPiHistoryReplaced` marks that query stale. The tool-result callback stops it, rotates the Claude session id to avoid racing the killed child's transcript writer, and imports Pi's new history with completed tool results before continuing. The stopped query's teardown drains its waiting MCP handlers with the cause `history-restart`, and `tool_calls_interrupted@history-restart` is `expected`: the drained answer reaches only the discarded child. If the child ran a connector or foreign MCP tool absent from Pi history, the query finishes on its original history and its persisted record requires a rebuild on the next turn. Query teardown must end the waiting callback stream even if the child's close throws. When the query had already ended (an overflow: Claude's request failed with "Prompt is too long", Pi compacted and retries from the tool result), the lane's `historyReplacedAfterQuery` makes that retry start a query with the same continue prompt instead of taking the orphaned-result path, which would end the turn. `tests/unit-compact-restart.mjs` covers these paths.
- A host that runs the bridge itself (not Pi) may restart while a turn waits for tool results, and the query that made those calls dies with it. The extension marks the API object it gets with `Symbol.for("kendex.pi.claude-bridge.host-resume.v1")`, and such a host sets `Symbol.for("kendex.pi.claude-bridge.host-resumed-turn.v1")` in the stream options of the request carrying those results. `src/index.ts::isHostResumedTurn` grants it only when the request is not cancelled, its context ends in a result for every tool call of the assistant message before them and nothing else, and no query of this process is in the lane or made one of the calls (`src/query-state.ts::idleForHostResume`). The request then runs in its own lane, not a fork lane, and skips the orphaned-result path. It marks the record `host-resumed` with `forceRotate`, because the killed child may still write the old transcript. It syncs Claude's session to the context plus a continuation prompt, so the rebuild imports every result and the query prompts with that text alone. The prompt is never in the host's history: the query's starting claim and the record's cursor and digests cover the host's messages only, so the next prompt resumes warm. Pi never sets the option, so every Pi path is unchanged. `tests/unit-host-resumed-turn.mjs`.
- Warm reuse of Claude Code's session is content-checked, not only count-checked. Claude Code resumes its own transcript, so every cursor write stores `historyDigest` (`src/history-digest.ts`) of Pi's messages `[0, cursor)` as the bridge imports them, plus `trailingAssistantDigest` for the reply Pi appends at the cursor, and REUSE requires both to match. A digest only ever describes history Claude holds: what REBUILD imported, a query's verified starting context, and then, at each tool-result callback, a suffix that must equal exactly what the bridge put into Claude's history since the last claim (`deliveredSuffix`: every reply delivered, in order, none missing or extra; results only for their calls and only if Claude received them; users only if this callback accepted them, written live or queued). The orphaned-result path, which delivers nothing, may add only results for calls the ended query made. A view that fails the check is never stamped; the record gets `UNVERIFIED_HISTORY_DIGEST` and `needsRebuild`, and restore keeps that mark. Records without a digest are accepted once and stamped. The digest covers order, roles, user text and images, assistant text and tool-call ids, exact Pi tool names and arguments. It deliberately ignores tool-result bodies and error flags, which pi-prune and pi-jev-pruner replace in every provider call, and thinking, system messages and metadata. `tests/unit-history-digest.mjs`, `tests/int-context-edit.mjs` (a same-length Pi `context_edit`).
- A rebuild never imports the latest assistant message with a thinking block removed: the API refuses a request whose latest assistant message's thinking differs from what it returned. So a trailing Claude turn with an unsigned thinking block (a stream cut mid-thought), and each one before it until the latest assistant replays exactly, is imported with its tool results as one user-side note. The turn wrote everything before any result came back, so the note lists its text and each numbered tool call's Pi name and arguments in the turn's own order, then each result's text and error flag by call number in history order, with nothing cut (`src/convert.ts::unreplayedTurnNote`). The note is a content array: a result's images are carried as the same image blocks the normal import builds, in their place among the results, and only an image without data or a MIME type is left as a text marker. The record's `historyDigest` still covers those messages as Pi has them, because Claude holds their content, so the next prompt's REUSE is legitimate. Each rebuild that writes a note writes the `unreplayable_turn_imported_as_note` diag entry. `tests/unit-sync-shared-session.mjs`, `tests/unit-import.mjs`.
- An unpaired `tool_use` in a rebuilt session is paired with an explicit `is_error` result saying the output was lost, never a bare placeholder a model reads as output. `src/tool-pairing-audit.ts`.
- `src/convert.ts::failedToolResultText` supplies the text-only failed-result projection for imports and native matching: text blocks in order, joined by newlines and trimmed, or `Command failed with no output` when no text remains. Pi retains the original result, including error images. Native matching also recognizes the block form in transcripts written by earlier imports, subject to the same image-evidence checks. `tests/unit-import.mjs` checks the import, and `tests/unit-native-enhancements.mjs` checks actual JSONL through a second rebuild with successful images as a control.
- A same-account rebuild (Case 4) starts from Claude Code's own transcript, and its first request reads the prompt cache only if the prefix it copies runs to within about 20 content blocks of the old request's end: the API looks for an earlier cache entry only that far back from a request's last breakpoint. `src/native-fork.ts::planNativePrefix` walks Pi's history and the old transcript's main chain together, a whole group at a time: a prompt, or an assistant message (its records sharing one message id) together with all of its tool results. It stops at the first group whose content differs. Claude Code's side is compared through the bridge's own transforms, because Pi stores what they produced: an assistant message as the stream records it (`mapToolName`, and `mapToolArgs`, which renames keys and leaves omitted bash timeouts absent), a prompt as `src/user-prompt.ts` builds it (one Claude Code prompt record may cover several of Pi's user messages in a row, joined as the bridge joins a batch; a batch runs to the end of Pi's context, so only Pi's whole run of user messages, followed by a message that is not a user's, matches that way), and a tool result as `toolResultToMcpContent` delivered it. Text, thinking with its signature, tool ids, names, arguments, result text, images and error flags must then be equal. A signed thinking block also matches on its signature alone, whatever text Pi holds: a Pi extension that labels thinking for display trimmed that text, and older versions of it wrapped the text in a colored label. The signature is the API's identity for the block, and the fork carries Claude Code's text, which is what Claude saw. A block without a signature never matches that way. A successful result whose delivered content is only blank text is compared as `(<tool> completed with no output)`, with the tool named as Claude Code's call names it: Claude Code stores such a result as that note (`hRr` in the claude binary of SDK 0.3.284). It stores a failed result as one string, the text blocks joined by newlines and trimmed, or `Command failed with no output` when that is empty. An image matches on equal base64 data and media type, or on a saved original whose bytes and filename's MIME type match Pi's image. `src/native-images.ts` reads evidence only from that transcript's own `tool-results` directory, rejecting files and directories linked outside the session. Only originals verified in the selected prefix are copied, and their bytes are checked again before the old session is removed. The original note text stays unchanged. SDK-tagged result records identify their added image notes through `toolUseResult`; image-source-like text supplied by Pi is compared as ordinary tool content. Missing or invalid evidence ends the prefix before a re-encoded image. Claude Code's self-answered calls and results match alongside the blocks Pi holds, and every such call must have its result before the prefix can include the turn. Records an earlier rebuild imported match in the import form instead. Claude Code's records without a Pi counterpart come along: attachments, meta and system records, and synthetic assistant records (the last only in front of a matched group). A `queued_command` attachment on the chain after a group is a steer the bridge delivered while the query ran, and it matches the run of Pi's next user messages it was built from (`planDeferredUserReplay` joins them into one prompt); one that matches none ends the prefix. The fork copies every transcript record up to the cut in file order, and Claude Code's loader stitches same-message assistant records and their tool results into the conversation even when they are off the parent chain. A parallel tool batch is written that way: each result is parented to its own call, and only the last result is on the chain. So a group also takes the off-chain results the loader stitches to its message (`stitchedRecords`, which follows sdk.mjs `a_e` as it runs on the fork, where `sourceToolAssistantUUID` is cleared), and each must equal Pi's result. The cut lies where the slice through it holds no user or assistant record besides the chain and those verified results (`lastCarriedExactly`). A result tied to the message only by its call's id ends the prefix, because Claude Code's own loader (`Uar` in the claude binary) adds that one only behind a feature flag. That loader also adds the attachment, system and meta records hanging off the chain beneath a tool-calling message or its results. Those are Claude Code's own and may come along, except a `queued_command` no group matched: it renders as the user message Pi holds too, and the import would write it again. So the slice through the cut holds no `queued_command` but the matched ones on the chain. The prefix is copied with the SDK's `forkSession` into a new session id, through an in-memory `SessionStore`. The SDK forks exactly the records that were verified, from the account's config dir, and never reads the process env. Pi's messages after the prefix are imported and chained from the fork's leaf, which is often an attachment. A missing or unreadable transcript, a line that does not parse, an unknown record shape, a compacted chain, no matching first group, or a failed fork all fall back to the full import. The fork is the one sync path that awaits, so `src/index.ts::awaitForkedRebuild` starts the query only after it settles. Meanwhile the lane reads as in use (`QueryContext.forkSyncPending`), for lane release and for request routing alike. The request is checked again right before its query starts, and a lane a session shutdown ended starts none. A request cancelled in that gap writes nothing, starts no query, and is marked like an abort. If the shared record changed in the gap, the fork is dropped and the sync runs again without one. After an abort the old transcript is never written; on the preserved-id path it is deleted once its replacement is written and verified. A write that fails after creating the new file removes it. `tests/unit-native-fork.mjs`.
- A Pi fork restores its parent's marker only in explicit parent mode and after checking the history fingerprint. Ordinary restoration rejects another Pi session ID. Markers record `piSessionFile` from `SessionManager.getSessionFile()` together with the Pi ID and scheduled native snapshot. `src/transcript-ownership.ts` compares canonical paths: a different file, a missing recorded path or an absent current file makes the source read-only. A symlink to the same file can prove ownership. Persistence-only Pi identity fields stay out of `SessionState`. `tests/unit-transcript-ownership.mjs`, `tests/unit-reload-restore.mjs` and `tests/unit-account-session-persistence.mjs` cover these rules.
- Read-only restored sources are marked `inherited` with `needsRebuild`. They are never resumed, persisted as owned or rewritten in place. The rebuild reads under the source working directory and writes a separate session under the current directory. The source may still be appending a record, so copying a verified prefix stops at the last complete line. `tests/unit-native-enhancements.mjs` covers parent ownership, cross-directory copying, image evidence and self-answered calls.
- Each SDK query, including a deferred continuation, resets its captured `transcriptCheckpoint`. Only a top-level nonsynthetic assistant envelope supplies its native session ID and record UUID; nested subagent messages and Anthropic message IDs are not checkpoints. `persistSession` copies the UUID to `SessionState.transcriptLeaf` only for the matching native session, and detached consumers cannot stamp a replacement record. The checkpoint is persisted with the opaque account ID, never its config directory. `tests/unit-transcript-checkpoint.mjs` covers capture, reset and session scoping.
- Before reuse or a same-account rebuild, an owned record with a checkpoint requires `inspectTranscriptAfterLeaf` to find that UUID as a parsed record and prove no later conversation input. New assistant replies, text or image prompts and queued-command attachments relinquish ownership with `transcript-written`; unreadable, malformed or incomplete evidence uses `transcript-unverified`. Both marks select the read-only rebuild path, even if compaction already requested a rebuild. Native tool results, system/meta records, synthetic replies and exact interruption markers are not new input. Inherited sources, forced rotations and account changes already use separate transcripts. `tests/unit-sync-shared-session.mjs` covers inspection and source preservation.
- Append inspection reads the full native file in O(transcript bytes) time on each checked sync and retains no transcript cache. A record with no observed checkpoint cannot detect external appends. Inspection observes the file before reuse; it does not lock out a writer that starts afterward. These limits require profiling or a separate concurrency design before adding an index or locking.
- The copied prefix ends before the trailing assistant turns `src/convert.ts::unreplayableTrailingTurns` names: the import replaces those with a note, but only for messages it imports. An earlier rebuild may have imported such a turn with its unsigned thinking dropped while a later reply followed it, and `/tree` can then make it the latest. `tests/unit-native-fork.mjs`.
- A rebuilt transcript never ends on a user record. Claude Code resumes one that does with a synthetic "No response requested." reply, which it writes to the transcript and sends to Claude as Claude's own. So a query that sends Pi's whole context prompts with everything after Claude's last reply (`src/user-prompt.ts::promptRunStart`): Pi's trailing user messages plus any failed or Esc'd reply among them, since the import drops such a reply and would leave the message before it last. A reply cut off by Esc reads as Claude Code's own `[Request interrupted by user]`, and a failed one adds nothing. `planNativePrefix` matches Claude Code's prompt record against that same run. A transcript that still ends on a tool result or a note gets a `<synthetic>` assistant record flagged `isVirtual` (`src/session-persistence.ts::endOnAssistant`). Claude Code 2.1.288 leaves that record out of the request and sends the tool result and the prompt as one user turn, as Pi's own Anthropic provider does, and a fork keeps the flag. The flag is undocumented, so `tests/int-esc-resume.mjs` fails if Claude Code stops honoring it. `tests/unit-sync-shared-session.mjs`, `tests/unit-native-fork.mjs`.
- The provider is registered natively and unconditionally, once, by the primary module instance: `src/native-provider.ts::buildNativeProvider` through `pi.registerProvider`, with `auth.apiKey.check` and `resolve` answering from the existence-only credential probes in `src/auth-presence.ts`, so Pi hides the models while no account is connected. Pi's registration is upsert-by-id and replaces the stored object, so `PRIMARY_INSTANCE_KEY` and `ACTIVE_STREAM_SIMPLE_KEY` in `src/index.ts` keep a reloaded child module from swapping in its own `streamSimple` closure. A host below the peer floor gets `NATIVE_PROVIDER_UNSUPPORTED_MESSAGE` once instead of a wrong registration. Both native entry points route through the Claude Code subprocess; there is no raw API path, which is what keeps billing on the subscription.
- The stream-idle watchdog counts silence at any point of a live request, before and after the first output (`src/stream-idle-watchdog.ts`). It pauses only while the bridge itself is the holdup: Pi holds no stream because it is executing a tool, or an MCP handler waits for a Pi tool result; the clock restarts when that wait ends. Every SDK message resets it, and Claude Code 2.1.283 keeps a healthy child talking: API `ping` events arrive as `stream_event`s during long generations, every main-agent tool execution (connector calls included) emits a `tool_progress` heartbeat each 30s, and an `api_retry` notice extends the deadline by the backoff it announces. A child that stays silent anyway is a wedged child. A rebuild owed to an earlier idle timeout stops with a nonretryable error if the API never begins a response again, rather than rotate accounts or emit an automatic-resumption event. `QueryContext.apiResponded` records SDK stream events and nonsynthetic completed assistant messages, including non-streaming replies. `tests/unit-failure-frames.mjs` checks the consecutive-stall behavior.
- Abort and idle-timeout teardown never waits on the child. The query leaves its lane synchronously (`src/query-state.ts::detachContext`), so a prompt Pi sends right after Esc starts a fresh query on a rotated session instead of joining the dying one, and the old context stops claiming the shared session record. `src/query-teardown.ts::abortSdkQuery` arms a settle grace that `src/consume-query.ts::consumeQuery` races every iterator step against, so handler drains, the `activeQuery` clear and the error to Pi happen even when `interrupt()` and `close()` leave the iterator pending forever. `tests/unit-query-lifecycle.mjs`.
- The bridge's debug and diag logs are written only with `CLAUDE_BRIDGE_DEBUG=1` (what the bridge still writes without it is listed under that setting in the README), and no log line carries a tool payload or user-authored message content. `src/debug.ts`, `tests/unit-debug-discipline.mjs`, `tests/unit-debug-payload.mjs`.

## Child-executed tools

Pi's tools reach the child over the in-process MCP server, so a `tool_use` coming back is the child asking Pi to run something. claude.ai connectors run the other way: they are the child's own MCP servers, reachable only inside that process. So a `tool_use` under the connector namespace is never mirrored into the Pi stream: no `toolCall` block, no turn boundary, no expected-result entry (`src/connectors.ts::isChildExecutedTool`, applied at the emission sites in `src/assistant-stream.ts`). Mirroring one made Pi write a synthetic `Tool <name> not found` error beside an answer built from the real payload, and a rebuild projected that false result into the child's conversation of record.

The same rule covers Claude Code's in-process meta-tools (`ToolSearch`, `ScheduleWakeup`), matched by exact name in `src/connectors.ts::isChildInternalTool`, never by prefix. The MCP-resource built-ins stay mirrored: a resource read is a real account-surface access and consuming hosts audit it through the Pi mirror. The classifier is a namespace plus an exact-name set on purpose; "any name Pi cannot resolve" would also swallow a genuine tool-name mismatch, which must stay a loud dispatcher error. A non-bridge `mcp__<server>__<tool>` name and a bare name with no bridge manifest entry are refused at dispatch without widening the classifier; seeing a foreign MCP call commits account routing, a rejected naming slip does not.

Consequences:

- A connector tool must reach the model under one name. `src/convert.ts::mapPiToolNameToSdk` passes connector names through unchanged and `src/index.ts::resolveMcpTools` never re-offers a connector-namespace tool under the bridge prefix; Pi history recorded before that rule can still carry aliased names.
- The child's result is observed, never re-delivered (`src/assistant-stream.ts::noteChildExecutedToolResults`, fed from the SDK's `user` message). The debug line records name, error flag and byte size only.
- A connector call draws no tool card. Pi's assistant content is text, thinking or a `toolCall` its loop dispatches, so a delegated call has no honest representation; that is an upstream ask.

### The audit trail

Each child-executed connector call (never a child-internal built-in) appends a session `CustomEntry` of type `claude-bridge-connector-call` (`src/connector-audit.ts`). A `CustomEntry` does not enter LLM context and `convertPiMessages` reads messages, not entries, so it can neither be dispatched nor projected into the child. Never use `CustomMessageEntry` for this: that sibling type enters context, which is the bug again. The record is `{ name, toolUseId, outcome, byteSize?, childSessionId?, reason? }`, and `outcome` includes `unobserved` for a call whose result never came back, written at teardown with its cause; recording is keyed on the `tool_use` id so either path reaching a call first writes the one record. The audit map is query-scoped and is not cleared by `resetToolTracking`, which runs at every child message boundary. Pi's `createBranchedSession` copies entries into a fork, which is harmless here, unlike the `claude-bridge-session` marker beside it, which carries a `piSessionId` guard for that reason.

## Connector enforcement

- Write denial is two-layered: the known write tools are passed as `disallowedTools` by exact id (the CLI's MCP permission matcher takes exact names or a whole-server glob, nothing in between), and a `PreToolUse` hook denies any connector tool classified as a write at call time. Classification is fail-closed over the connector namespace: a tool is a write unless its name opens with a read verb matched as a word across naming styles, a leading server-name word skipped first; a name that opens with a read verb but also names a mutation is a write, and so is a name that does not parse. `src/connectors.ts::isConnectorWriteTool`, `tests/unit-connector-writes.mjs`.
- Every connectors-mode child also carries `src/connectors.ts::connectorBuiltinAllowlistHook`: only `mcp__custom-tools__*`, `mcp__claude_ai_*` and `CONNECTOR_DISCOVERY_TOOLS` may execute, and a hook exception converts to a deny because the CLI treats a thrown hook as fail-open. Connector sessions ingest untrusted third-party content, and a denylist of today's built-ins fails open on tomorrow's. The account probe child gets `denyAllToolsHook`.
- `settingSourcesForQuery` passes `["user"]` for connector queries and `[]` otherwise. `project` or `local` would let a checkout's `.claude/settings.json` reintroduce through `env` and `apiKeyHelper` exactly the provider-override environment `src/account-router.ts::subscriberProfileEnv` scrubs from managed children. An explicit `provider.settingSources` in bridge config wins verbatim.
- The same settings sources gate Claude Code's own instruction files: `"user"` loads `~/.claude/CLAUDE.md`, `"project"`/`"local"` the checkout's `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` and `.claude/rules`. Pi's system prompt already carries Pi's context files, so `buildClaudeQueryOptions` always passes `settings.claudeMdExcludes` for all of them. Managed/policy memory cannot be excluded. `tests/unit-instruction-files.mjs`.
- `enableConnectors` and `connectorWriteMode` resolve from user scope and the environment only (`src/config.ts::USER_SCOPE_ONLY_PROVIDER_KEYS`); project trust covers ordinary options and nothing that exposes live account data. `connectorWriteMode: "allow"` is per process, so an approved-write executor sets it in the child environment of a one-shot process.

## Config channels

`src/config.ts::loadConfig` reads `<piUserDir>/claude-bridge.json`, then a trusted project's `.pi/claude-bridge.json`. Provider options live under `provider`, and prompt replacement options live under `systemPrompt`. The loader normalizes provider values after merging both files. Connector enablement and write access remain user-scoped even for trusted projects.

## Runtime

- `src/account-router.ts::claudeChildEnv` builds every query, account-probe and model-discovery environment after profile-specific credential routing. It removes inherited Claude session identifiers, messaging state and effort, then sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` on the child copy. Callers add their tool, connector, compaction and effort settings afterward. Extension registration leaves the parent's environment unchanged. `tests/unit-child-env.mjs`, `tests/unit-model-discovery.mjs`, `tests/unit-account-rotation-stream.mjs` and `tests/unit-extension-load.mjs` exercise these boundaries.
- `mapToolArgs` preserves omitted and explicit bash timeouts across streamed calls, completed calls and MCP dispatch. Windows PATH lookup uses `.exe` names for both `claude` and `claude-code`; configured paths and isolated mode retain precedence. `tests/unit-tool-forwarding.mjs`, `tests/unit-tool-name-map.mjs` and `tests/unit-isolation.mjs` cover these contracts.

`requestLaneFor` gives one-shots their own fork lanes. Only a callback to an existing auxiliary query can reuse such a lane; historical tool IDs from the main conversation cannot claim it. Fork ownership determines ephemeral cleanup. When a reply to tool results fails, Pi's retry consumes `QueryContext.failedCallback`, a nonpersisted authorization created only for a retryable emitted error. `FreshQuery.syncMessages` adds the transport-only continuation prompt while cursors and digests describe Pi's messages. Account retry retains the continuation reason; cancellation, history replacement, and a new prompt clear the authorization. `tests/unit-transient-retry.mjs` exercises these paths through the provider and Pi's agent loop.

- Pi loads `src/index.ts` directly and supplies `@earendil-works/pi-ai` and `@earendil-works/pi-coding-agent` at runtime, so they are optional peers and only installed as dev dependencies for typechecking and tests. `zod` is pinned to 4.4.3, the version dot314's bundle shipped when this repository dropped its own.
- Pi's TypeScript loader does not keep a reassigned `export let` in sync for importers, and on `/new`, fork, or resume it reuses the loaded modules while passing the extension a new API object. Shared module state is therefore read through functions such as `getExtensionApi()`. `npm run check:exports` rejects `export let` and `export var` in `src/`, and `tests/int-session-new.mjs` checks that the provider survives `/new`. Unit tests run under tsx, which keeps real ESM bindings and cannot catch this.
- Startup preflight (`src/claude-executable.ts::preflightClaudeExecutable`) preserves `code`, `errno`, `syscall`, `path`, `cwd` and the detected executable file type on the error it hands the SDK.
- Relative imports in `src/` name the `.ts` file (`./config.ts`, not `./config.js`). Pi's TypeScript loader tries a `.js` specifier several ways and fails each try before it finds the `.ts` file. Across the bridge's imports that cost about 0.4 s per load on Pi 0.99.2, paid on every start, every `/reload` and every subagent child. `npm run check:imports` rejects a relative `.js` specifier in `src/`, and `tsconfig.json` sets `allowImportingTsExtensions` for it.

## Agent notices

With `agentNotices: true` in the user `claude-bridge.json`, an anomaly is queued for the Pi session whose request hit it and told once per kind, in one `claude-bridge-notice` message that the session's `before_agent_start` returns with its next prompt (`src/agent-notice.ts`, `tests/unit-agent-notice.mjs`). `src/config.ts::agentNoticesEnabled` reads the switch from the user file alone, when an anomaly is noted and when a notice is taken, so every loaded copy agrees and an edit needs no `/reload`; a project's file never counts, since it would add messages to the conversation. `CLAUDE_BRIDGE_DEBUG` does not turn notices on or off. It only decides the notice's last line: with it, the line points at the debug and diag logs; without it, the line says the details were not recorded and how to record them. A kind is told when the bridge showed Claude or Pi an error for it, or recovered from it on its own; expected cleanup (a cancelled request, a max-tokens stop, a history restart) and reports from the API or Claude Code are not told. The told kinds and their sentences live in the one `TOLD` table in `src/agent-notice.ts`, keyed by diag label. A new anomaly needs a sentence there, and its site calls `noteAnomaly` with that label; a label missing from the table fails the typecheck.

Only a session a person types into is told. Pi's `input` event fires before `before_agent_start` for the same prompt, and `notePromptSource` marks the session a person's for good when the input's `source` is `"interactive"` and `ctx.hasUI` is true. A subagent never qualifies: an in-process child calls Pi's `prompt()` with no UI (its source defaults to `"interactive"`, so `hasUI` is what rules it out), a background child prompts with no UI or over RPC (`"rpc"`), and a Herdr pane child, which has a TUI, gets its prompts through `sendUserMessage` (`"extension"`). This uses only Pi's API, never pi-subagents' environment variables. A person's session that prompts also takes what the process's subagent sessions queued, as `subagentKinds`, once per kind for that session; a child in another process is told nothing. `tests/unit-agent-notice.mjs`.

## Rate limits

`src/rate-limit.ts::normalizeRateLimitUtilization` reads a value in `(0, 1]` as a fraction and `(1, 100]` as a percent; exactly `1` is ambiguous and resolves to full, the fail-closed direction. `formatAllowedRateLimitWarning` emits a neutral toast from `ALLOWED_RATE_LIMIT_WARNING_UTILIZATION_THRESHOLD` up and never quotes a `% used` figure. Rate-limit errors are deduplicated before notification and emitted as `pi-claude:rate-limit`.

Usage credits require `provider.allowUsageCredits: true` in the user `claude-bridge.json`. `src/consume-query.ts` checks `rate_limit_event.rate_limit_info.isUsingOverage` even while Pi executes tools and no response stream is active. Detection interrupts the SDK query and returns a `usage-credits` failure, which enforces the user's billing choice rather than indicating an account failure. It never rotates profiles or emits the rate-limit event used for automatic resumption. A pending history restart ends with the billing error, and deferred continuations stop. Existing failure handling retains completed replies and reports a failure after a delivered tool turn through its result callback. The interrupted session is marked for a rebuild with a new Claude session id, because its child may still write to the old transcript. `tests/unit-usage-credits.mjs` and `tests/unit-continuation-failure.mjs` exercise these paths offline; the guard cannot prevent a charge made before the event arrives.

## Tests

```bash
npm run typecheck
npm run test:unit      # node --test over tests/unit-*.mjs, no credentials
npm run test:ci        # typecheck, then the unit suite
npm test               # unit, then the integration suites
npm run test:usage     # A/B subscription-usage comparison against Claude Code direct
```

`test:unit` preloads `tests/lib/test-env.mjs`, which points `PI_CODING_AGENT_DIR` at a scratch directory so unit tests never read the real `claude-bridge.json` or append to the real bridge logs. To run one file, keep the preload: `node --import tsx --import ./tests/lib/test-env.mjs --test tests/unit-foo.mjs`. `tests/unit-test-env.mjs` fails when it is missing. The integration harnesses give every suite its own debug and diag log under `.test-output/`.

Tests use Pi 1.5.0 and import `pi-agent-core` directly for its real agent loop. The dev-only `typebox` dependency matches Pi's schema builder for tool fixtures. `tests/lib/pi-frame-consumer.mjs` checks append-only event ordering and runs Pi's `toJsonEvent` on updates, including delayed consumption; Pi 1.5 has no frame encoder or reducer exports. Prompt tests use the package's installed builder. `tests/unit-prompt-appendages.mjs` also loads dot314's sibling `model-sysprompt-appendix` extension with fixture configuration to verify appended instructions reach the outbound query.

Run `node tests/cache-updates-probe.mjs` from the bridge directory to check instruction changes, tool additions and removals, and cache reuse against the compiled bridge. It spends real Haiku 5.5 subscription usage, with usage credits disabled by the bridge guard. Each run saves replies, token counts and rate-limit status in `.test-output/cache-updates-<timestamp>.json`; scratch sessions are removed with `trash`.

The integration suites (`tests/int-*.sh`, `tests/int-*.mjs`) need the `pi` CLI and a logged-in Claude Code; `tests/int-session-resume.mjs` also needs `CLAUDE_BRIDGE_TESTING_ALT_MODEL` and `CLAUDE_BRIDGE_TESTING_ALT_PROVIDER` from `.env.test`, which `npm test` sources when present. They read bridge settings from the agent directory they run under (`PI_CODING_AGENT_DIR`, else `~/.pi/agent`). The shell suites bound each run with `run_with_timeout` from `tests/lib/bash-setup.sh` because macOS has no `timeout`. `test:usage` spends real subscription usage. A test that spawns a child pins `HOME`, `PI_CODING_AGENT_DIR` and `CLAUDE_CONFIG_DIR` explicitly, because a spawned child inherits the process's start environment rather than a harness override.

## Syncing with dot314

This repository is `git subtree split --prefix=extensions/pi-claude-bridge` of [w-winter/dot314](https://github.com/w-winter/dot314) plus local commits. Splitting dot314 again produces the same commit ids, so its bridge changes merge normally. In a dot314 clone with `upstream` pointing at w-winter/dot314:

```bash
git fetch upstream
git subtree split --prefix=extensions/pi-claude-bridge upstream/main -b bridge-upstream
```

Then, in this repository:

```bash
git fetch <dot314 clone> bridge-upstream
git merge FETCH_HEAD
```

Upstream commits regenerate `bundle/index.js`, which this repository does not keep. Resolve those conflicts with `git rm -r bundle`.
